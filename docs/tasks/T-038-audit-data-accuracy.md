# T-038: Audit: data accuracy

- **Milestone:** quality · **Depends on:** none · **Model tier:** strong (Codex Sol)
- **Runs in parallel with:** T-037 (no data loss). Stay inside your file areas below; if a fix needs a file outside them, describe it in the Handoff instead of editing.

## Goal

The owner asked for proof that every number the app shows is right: imported history matches Strong, weights are stored exactly as typed, and every calculation (e1RM, hard sets, volume, recent vs baseline, daily/weekly grouping) is correct. Check each against hand-worked examples and the research report, prove any error with a failing test, fix it, and leave a written verdict per area.

Never read or copy `export_data/` (the owner's real data); use synthetic fixtures only.

## What to check (each needs at least one test with hand-computed expected values)

1. **Import parsing:** both Strong layouts, quoted fields with commas and newlines, set-order codes (W, D, F, numbers), RPE blanks, durations, distances, seconds, notes, measurements file, BOM and CRLF, time zones (local timestamps), duplicate rows.
2. **Units:** lb → kg → lb round-trips display exactly what was typed (e.g. 135 lb, 225 lb, 2.5 lb plates); per-exercise unit inference; no rounding at storage; display rounding rules.
3. **e1RM and effective reps:** worked examples from the report; RPE missing; reps above the formula's valid range; warm-ups and incomplete sets excluded; bodyweight and timed exercises excluded.
4. **Hard sets and volume:** warm-ups excluded everywhere (hard sets, volume, tonnage); drop and failure sets counted per the report; fractional primary 1 / secondary 0.5; one set never counted twice for the same muscle.
5. **Dates:** grouping by the phone's local day and Monday-start weeks across DST changes and around midnight; workouts spanning midnight.
6. **Recent vs baseline and range statistics:** window edges, zero baselines (no Infinity/NaN), missing days zero-filled.
7. **History totals:** per-workout set counts and volume match the sets shown.

- **Findings by area (1–7):**
  1. **Fixed — import parsing.** `parseDecimal` accepted `1e309`/`-1e309` as infinite numbers; workout and measurement parsers consequently accepted infinite values. It now rejects nonfinite results with the existing source-column/row errors. `parseStrongDuration('1e308h')` overflowed when multiplying a finite hour count by 3600; unreadable/overflowing durations now return null. A finite `1e308`-second duration also crashed planning at `toISOString()`; an unrepresentable end now remains null while its 100×5 set still contributes **500 kg**. A finite `1e308`-inch measurement overflowed during conversion to cm; the parser now rejects nonfinite converted values too. Both have separate before-fix failing tests in `StrongImportPlan.test.ts` and `StrongMeasurementsFile.test.ts`. Measurement fields did not share workout parsing's whitespace policy: a padded timestamp was refused, and `31, IN ` silently became 31 cm instead of 78.74 cm. Date, value and unit fields are now trimmed before interpretation. Regressions: `parseDecimal.test.ts`, `StrongWorkoutsFile.test.ts` (overflow cases), `StrongMeasurementsFile.test.ts` (two whitespace cases and overflow). Additional `StrongImportPlan.test.ts` audit example covers BOM, CRLF, quoted commas/newlines/quotes, W/numeric/D/F, unknown RPE, distance 1500.5 m, duration 90 s, workout notes, midnight-spanning duration, and identical adjacent drop rows. Hand result: 100×5 + 2×80×8 + 70×6 = **2200 kg**, 6 sets including warmup. Existing newer-layout/measurement/CSV/timestamp tests cover semicolons, decimal commas, notes/rest rows, inch/lb conversion and local-time DST ambiguity.
  2. **Correct under the documented unit heuristics — units.** Added `Weight.test.ts` examples: **135 lb = 61.23496995 kg**, **225 lb = 102.05828325 kg**, **2.5 lb = 1.133980925 kg**; each returns exactly the typed display value. A 102.499 kg storage value remains 102.499 even when displayed as 102.5. Existing `ExportUnitResolver.test.ts` proves per-exercise votes, ties/no-evidence defaulting to kg; existing plan tests prove exact exported kg retention, unrounded lb conversion and owner overrides. Inference and quarter-step display snapping are heuristics, not proof of the historical entry unit: round-only exports are inherently ambiguous, and converted fractional pounds are not inferred by the whole-pound grid. Keep the override review. No storage snapping was added. Unrepresentable durations are treated like unreadable informational durations, without discarding performed sets.
  3. **Fixed — strength query date reference; formulas correct against the report.** `ExerciseStrength` grouped sessions into local date labels but compared those labels' UTC midnights with the actual instant. Just after midnight in Riyadh, a performed 100 kg single disappeared from the trend; near midnight in Los Angeles, the 28-day rate boundary expired early. The query now passes today's local date indexed at UTC midnight to the trend, while its SQL still excludes genuinely future workouts by instant. New `ExerciseStrength.test.ts` regressions prove **100 kg** immediately after local midnight, **102.8346868942621 kg** EWMA / **+2.8346868942621%** weekly change from 100→110 kg over 7 days, and the inclusive 28-day civil-date boundary.   4. **Correct — hard sets and volume.** Existing `HardSets.test.ts`/`MuscleVolume.test.ts` prove RIR ≤4 (RPE ≥6), unknown effort, failure overriding effort, warmup/planned exclusion, 1 primary / 0.5 secondary (optional 0.3), zone edges and >11 session flags. Added `WeeklyMuscleVolume.test.ts` proves three working/drop/failure sets yield **3 chest / 1.5 triceps** and that the real schema refuses two roles for the same exercise/muscle, preventing join multiplication. Added plan/history checks prove warmups contribute zero tonnage; drop/failure loads contribute normally. There is no cited extra multiplier for drops or failure, so each qualifying performed row counts once.
  5. **Fixed — daily iteration at midnight DST transitions.** Santiago's 2024-09-08 starts at 01:00. Carrying that hour into Sep 9 skipped the last selected day. Calendar increments now reset to the next day's local start. `DailyHardSets.test.ts` proves **Sep 8: 1, Sep 9: 2**, along with existing Riyadh midnight and spring/autumn DST cases. Added midnight-spanning workout example: New York Sunday 23:50 start, Monday completion/finish → **Sunday 1 / Monday 0**, Monday-week **Mar 4: 1 / Mar 11: 0**. The pre-existing weekly DST test now explicitly pins New York, so it exercises real offset changes regardless of the host zone. Existing `StrongTimestamp.test.ts`, `localDate.test.ts`, calendar and month-group tests cover local timestamps, leap dates and grouping.
  6. **Correct — recent/baseline and range statistics.** Existing `RecentVsBaseline.test.ts` hand example: 21 days×2 + 7 days×4 → **recent 28, baseline 17.5, +60%**; it proves inclusive window edges, rest-day gaps, weekly cadence, zero baselines, decimal boundaries and selected statistics. Range statistics count supplied observations; daily query zero-filling supplies rest days, while irregular strength observations intentionally remain sparse.
