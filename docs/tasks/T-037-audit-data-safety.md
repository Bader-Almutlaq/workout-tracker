# T-037: Audit: no data loss

- **Milestone:** quality · **Depends on:** none · **Model tier:** strong (Codex Sol)
- **Runs in parallel with:** T-038 (data accuracy). Stay inside your file areas below; if a fix needs a file outside them, describe it in the Handoff instead of editing.

## Goal

The owner asked for proof that the app never loses or corrupts data. Hunt for every path where a workout, set, template, exercise, measurement or setting could be lost, duplicated or silently changed, prove each risk with a failing test, fix it, and leave a written verdict per area.

## What to check (each needs at least one test that would fail if the risk were real)

1. **Opening storage:** failed/locked open never deletes or reinitialises the pool; retries; clear error. Second-tab case.
2. **Migrations:** snapshot before every pending migration; a migration that throws leaves the database unchanged (transaction) and the snapshot restorable; running migrate twice is a no-op; v1 → v3 on a populated database keeps every row.
3. **Backup → restore round trip:** every table and column survives byte-for-byte (workouts, sets with all fields, notes, kinds, entry units, RPE, templates with folders/sets, custom exercises, aliases, merges, measurements, settings). Restore takes a safety snapshot first; a corrupt or older/newer-schema backup is refused without touching current data.
4. **Import:** idempotent (importing the same export twice adds nothing); one transaction (a failure part-way leaves nothing behind); snapshot first; importing after app-logged workouts keeps them.
5. **Live workout:** every write (add/edit/delete set, reorder, change kind, notes, finish, discard) persists immediately; a reload mid-workout restores exactly; only one in-progress workout; discard deletes only that workout; finishing twice is harmless.
6. **Deletes and merges:** deleting a workout, template, folder or custom exercise never cascades into other data unexpectedly (e.g. an exercise used in history must not be deletable or must be merged, never dropping sets); merging exercises moves every set, template entry and alias.
7. **Worker API:** every write method notifies listeners and surfaces errors (no swallowed promise rejections).

- **Findings by area (1–7):**
  1. **Opening storage — fixed.** Existing pool-preservation flags and lock retries pass regression tests. A failed launch after opening SQLite previously left its connection open; a failing migration-snapshot test proved the missing close. `OnDeviceStore.open` now closes on initialization failure without deleting storage. `src/worker/OnDeviceStore.test.ts` covers a second-tab-style lock followed by success, exhausted retries with a readable error and unchanged files, and snapshot failure with unchanged live bytes and a closed connection. These tests exercise real SQLite with simulated pool I/O, not actual Safari locks.
  2. **Migrations and local snapshots — safe / fixed.** `Database.test.ts` verifies every old row and column through an actual populated v1 → v3 upgrade, migration reruns with identical exported bytes, rollback of a failing pending migration, and reopening its original snapshot. Existing transaction/savepoint tests also pass. Worker tests verify that a populated v1 database is copied before v2/v3 run and that snapshot failure prevents migration. Two snapshot regressions failed before fixing names: equal timestamps overwrote the previous copy; a clock moved backwards caused pruning to delete the snapshot just returned. Names now advance by at least one millisecond beyond the newest saved snapshot. The newest three remain the retention policy. One snapshot protects the complete pending migration batch, taken before any migration runs; each migration retains its own transaction, so an earlier successful migration remains applied if a later one fails. This follows the existing storage policy rather than adding one file per migration.
  3. **Backup / restore — fixed.** Validation formerly accepted a missing set-notes column, orphaned foreign keys (`quick_check` still reported `ok`), and an unexpected trigger capable of deleting history on the next setting write. Each failed its new regression before the fix. Validation now compares each known table's complete stored schema definitions (including indexes, constraints and triggers) against the frozen migrations, and runs `foreign_key_check`. `BackupValidation.test.ts` covers these cases plus damaged pages, missing tables, garbage and future schemas. `BackupRestore.test.ts` proves byte-identical full-database round trip, every table/column/value and id sequence, the exact pre-restore snapshot, invalid-input refusal before replacement, snapshot failure, replacement failure with rollback, rollback failure with an actionable snapshot name, and restoring a real v1 backup into v3. The synthetic fixture includes all set fields, all kinds, notes, kg/lb units, RPE, sides, rest/completion state, active work, custom/Strong exercises, merged-name aliases, muscles, measurements, settings and complete templates/folders/sets.
  4. **Import — safe, with coordination fixed in the worker.** Existing `StrongImporter.test.ts` proves same-export idempotence and transaction rollback after a later workout/set fails. The added preservation test proves that app history, an active workout, templates, measurements and settings survive import and reimport. Worker tests prove that import/merge snapshots contain exactly the pre-write data, and that failed snapshots prevent all writes and notifications. A paused-import regression proved restore could previously overtake its safety snapshot and then receive the old import's writes. All asynchronous worker requests now run in submission order through their entire snapshot/restore lifecycle. Reimport idempotence means unchanged owner records and zero added rows; SQLite's `INSERT OR IGNORE` may consume unused AUTOINCREMENT ids, which is harmless and deliberately not treated as data loss.
  5. **Live workout — fixed.** Repeating finish previously rewrote `endedAt`; finishing an already-deleted empty workout threw. Repeating an explicit completion request rewrote its timestamp/rest. These are now no-ops, with regressions in `WorkoutLogger.test.ts`. Nonfinite/negative set durations were accepted (NaN silently became SQL NULL); a NaN rest target silently erased the stored choice. Regression tests proved both before adding typed input errors. `WorkoutLogger.test.ts` now reopens real SQLite bytes after each add/edit/delete/reorder/kind/unit/completion/workout-note operation, checks exact state, and verifies discard deletes only its workout tree. Existing tests cover finishing/cleanup, one active workout (also enforced by the unique database index), planned/completed separation and validation. `RestTimer.test.ts` proves nonfinite targets leave the stored choice unchanged. Physical crash durability on an iPhone is not proven by an in-memory export/reopen test.
  6. **Deletes / merges — safe, with rename matching fixed.** A rename followed by a later Strong import previously created a second exercise; its regression failed before preserving the old name as an alias during update. `ExerciseEditor.test.ts` verifies every history/template entry and alias moves on merge while every set field stays identical, batch failure rolls back, and foreign keys refuse deleting an exercise used in history or only in a template. There is no custom-exercise delete endpoint: hiding uses archive. `TemplateStore.test.ts` proves deleting a folder preserves its templates and children; deleting a template only clears history's `templateId`, preserving all workout/set/exercise/measurement/setting records; a replacement that fails after deleting children restores the entire original template. Workout discard isolation is covered in area 5. Canonical merge retains the target exercise's identity/metadata, with the existing documented default-unit adoption rule.
  7. **Worker API — fixed.** `WorkerApi.test.ts` proved partial start/add batches could commit before a later invalid exercise caused rejection without notification. Each request now wraps its logger actions in one outer transaction. A broken subscriber previously rejected a successfully committed write and prevented other listeners from running; synchronous throws and remote promise rejections are now logged independently, and healthy subscribers still run. A single integration test invokes every database-mutating endpoint and requires one notification on success, rejection without partial data on representative failures, and successful later requests after rejection. Separate tests cover restore-time writes waiting for the reopened connection and restore not overtaking an import. Subscriber transport failures are logged, not reported as failed database commits. The pre-existing `startFromTemplate` stale-screen refresh before rejecting an already-active workout is retained.
